# Phase 5 bounded transfer contract v1

Simulated, design-stage prototype; physical validation pending.

The opt-in `platform-transfer-reference@1.0.0` preset adds a normally-open tie and original-path isolator for each declared recipient platform. The existing Generation III designs remain non-transferring unless this preset is selected deliberately. Generation II and III comparisons use the same platform inventory, node demand, environment, batteries, horizon, and initial-condition procedure; only the declared switching equipment/policy differs.

The supported active model is one-hop, radial, whole-platform bundles. Every recipient has exactly one donor, one original feeder, one receiving bus, one isolator, and one tie. Donors cannot themselves be recipients. No active mesh, parallel supplies, automatic retransfer, or fractional-platform admission is supported. Physical asset ownership never changes. A failed receiving bus/downstream asset is never repaired by a source change. All routes share the real shore source; a shore fault has no transfer benefit.

`src/twin/transfer/types.ts` owns policy `platform-transfer-1`, topology `single-hop-radial-1`, design extension version 1, and checkpoint extension version 1. `Design.transfer` is optional and `SimulationState.transfer` is present only for opt-in designs. Project/state schema 3 remains the compatibility envelope; legacy checkpoints without this extension retain prior behavior. The extension is included in engineering identity. The new transfer physical model identity is `neptune-transfer-1`; existing designs preserve their model/solver interpretation.

`src/twin/transfer/controller.ts` owns deterministic controller/allocation. `src/twin/transfer/design.ts` installs the preset and validates explicit asset references and immutable equipment records. `src/twin/transfer/demonstrations.ts` declares small eligible/no-benefit/capacity comparisons. Engine integration is in `src/twin/engine/simulation.ts`; all whole-run metrics remain in the existing experiment runtime.

Each recipient's states are normal, detected, isolated, evaluating, waiting, transferred, blocked, or lockout. Detection and successful isolation/evaluation can share one simulation timestamp but emit distinct stable sequence-numbered transitions. Isolation must be positively confirmed before tie closure. Attempts have stable IDs; one attempt is allowed per recipient per run. A failed isolation locks out. An ineligible request blocks. Eligible requests wait the configured finite delay (0–60 s, multiples of 0.125 s). Pending execution rechecks all faults, capacity, and interlocks. Fault clearance before closure cancels safely. After closure, original remains open even if restored. Donor/tie failure or lost capacity opens the tie and locks out; reset/reinitialize starts a new run.

At each boundary, admitted external events execute in persisted sequence before transfer deadlines. Transfer deadlines split physical integration intervals, including between ordinary solver steps. Faults at the exact deadline therefore prevent closure. Requests allocate by persisted ascending integer priority then stable recipient ID. Native loads consume shared resources first. Transfer requests are atomic indivisible bundles; partial restoration means some distinct recipient platforms are admitted and others remain unserved. No reservations are spent during the delay; allocation is recomputed atomically when closing and throughout transferred operation. A refused bundle records its binding resource and headroom. Higher-priority native load is protected before any transferred load. Lower-priority transferred bundles shed first when headroom falls.

Resource accounting uses full supported restoration demand (whole installed nodes at declared workload plus pumps, controls, network auxiliaries and conversion losses), not the de-energized observed draw. Each bundle consumes the common source/conversion resource, donor feeder/bus, tie, receiving equipment, and module distribution limits once. Recharging is subordinate to load and must not spend capacity reserved for service. The switch feeds actual electrical dispatch; thermal, hydraulic, storage, and required-network service continue to constrain useful service.

Transition evidence includes timestamp, stable transition/attempt IDs, previous/new state, reason, affected physical assets, original/donor paths, original/tie positions, admitted/unserved watts and accelerator inventory, binding resource and measured headroom. Keep exact cumulative counts and current allocation after bounded transition detail truncates. Checkpoints persist the complete extension and validate its design identity, policy/version, current switch positions, pending deadlines, sequence, and cumulative evidence. Structural/policy edits require reinitialization. Economics and views do not.

New generic tie/isolator ratings, dimensions, mass and prices are illustrative reference assumptions, not vendor specifications. The initial catalog models zero incremental conversion loss and no actuator/standby draw; switching transients, protection coordination, cables/civil works, commissioning and vendor pricing remain excluded and are displayed in reports. Existing source/conversion losses remain charged to both native and restored loads.

The independent fixtures cover A–H in the request, including resource boundaries, simultaneous requests, mid/post-transfer faults, exact deadline ordering, checkpoint/replay/import/worker lifecycle, malformed and unsupported inputs, thermal/network coupling, and actual browser exports. A 100 kW/60 kW/two 30 kW arithmetic fixture must admit one bundle and leave 10 kW; it is a test oracle, not installed equipment.
