# Phase 1 numerical boundary audit

Scope: the four standalone solver modules, their directly callable helpers, and the boundaries used by the coupled engine. This is numerical input/output safety within the existing reference model. The single-phase circuit, equipment defaults, thermal equations, electrical efficiencies, offered-traffic assumptions and generation policies are retained. It is not physical validation.

## Shared failure contract

`src/twin/safety.ts` defines `SimulationError`, `FailureDiagnostic`, `failure`, `finiteNumber` and `finiteOutputs`. Invalid numerical values use `invalid-input / INVALID_NUMBER`, an affected field, units and the applicable numeric constraints. Received nonfinite values are represented as strings in diagnostics, so JSON cannot turn them into a misleading `null`. Boolean input failures use `INVALID_BOOLEAN`.

Valid inputs outside implemented capabilities use `unsupported-configuration`. A successful calculation with insufficient supply/flow/network capacity remains a solved inadequate condition. Arithmetic overflow/underflow and unresolved hydraulic crossings use `numerical-failure`; they do not become nominal successes or receive a physically plausible clamp. Resource admission is distinct from arithmetic failure.

`finiteOutputs` validates returned scalar quantities. The solvers additionally check critical intermediate arithmetic before min/max, division, logarithms or a subsequent stage could hide a nonfinite value. Network bottlenecks contain validated capacities and finite checked resource loads. All standalone solvers are pure with respect to their arguments. Engine candidate-state validation and transactional worker publication are recorded separately in `CONTRACT.md` and tested by the integration requirements.

## Optional pump inputs: PH0-001

An absent own `shutoffPa`, `freeFlowM3S` or `efficiency` selects the existing 250,000 Pa, 0.1 m³/s or 0.72 default respectively. A supplied `undefined`, `null`, `NaN`, either infinity, string, boolean, array or object is rejected. Shutoff and free flow must be finite and strictly positive; efficiency must additionally be at most one. Invalid supplied ratings also reject a disabled circuit rather than hiding behind an early zero-flow return. A correctly specified pump count of zero or speed of zero still returns an exact zero result.

`tests/phase1-numerical.test.ts` exercises this behavior against current code. PH0-001's original reproduction and archived source are immutable historical evidence; the Phase 1 acceptance record records the isolated historical diagnostic separately.

## Bounded work and convergence

The hydraulic solver retains bisection and its maximum of **60 iterations**. It requires a flow bracket no wider than `min(1e-12 m³/s, freeTotalM3S × 1e-10)` and a head residual no larger than `0.01 Pa + shutoffHeadPa × 1e-10`. The midpoint is calculated without adding both potentially large endpoints. Representational stagnation is detected. An unresolved crossing throws `HYDRAULIC_NONCONVERGENCE` with iterations, head residual, bracket width and flow tolerance. Intermediate overflow uses `NONFINITE_OUTPUT`; a positive pump operating envelope rounded to zero uses `HYDRAULIC_UNDERFLOW`.

The nonconvergence test uses an actual finite 1e8 m³/s free-flow bracket, an oversized finite pipe and zero losses. The calculation reaches floating-point bracket stagnation; the test does not mock convergence or merely assert an iteration counter. Separate overflow tests use actual finite inputs that overflow pump affinity arithmetic, Darcy division, battery energy-to-power conversion, summed requests, exchanger capacity or thermal heat partition. These extreme standalone inputs are safeguards tests, not supported equipment recommendations.

Electrical, thermal and network work contains no unbounded numerical iteration. Network graph expansion validates at most 160 nodes and 40 racks per module before inventory loops; graph collections use the shared structural limit. Search propagation visits bounded arrays/queues, including cyclic/ambiguous topology. This does not claim that every maximum admitted graph executes economically; overall engine/worker replay resource budgets are separate in the shared contract.

## Unavailable quantities and signed outputs

`NetworkAssessment.maxUtilization` is `number | null`. A positive offered load against zero capacity has no finite utilization ratio; a positive but extremely small capacity can likewise have a ratio that is unrepresentable. These cases return explicit `null`, retain finite offered-demand/capacity evidence and report `violated`. Even a sub-bit/s positive load at zero capacity is a shortfall. Ordinary finite-capacity bottleneck tolerance remains the existing `max(1 bit/s, capacity × 1e-9)`. No current UI consumer performs arithmetic on `maxUtilization`; the sole prior numerical consumer is the existing default-capacity test.

Zero flow, zero UA, disabled electrical/pump circuits and zero network demand are physical controls. Heat transfer, ambient heat and stored heat can be signed. The guards do not turn reverse heat flow into zero or reject a physically allowed negative result merely because it is negative.

## Remaining model limits and compatibility

- These guards retain assumed pump curves, fixed fluid properties, the linear air boundary, fixed electrical efficiencies and illustrative offered-traffic demand. They add no vendor-calibrated equipment envelope, dynamic network routing or generation transfer policy.
- Arbitrarily large but finite standalone inputs may be numerically unrepresentable and fail explicitly. No hidden upper equipment rating is invented to force an answer. The coupled project configuration has its own existing bounded model envelope.
- A finite output is necessary but does not establish physical accuracy. Engine checkpoint/state validation must still reject incoherent or unsupported state before committing or restoring it.
- Missing grid-domain capacity is now an explicit input error; callers that intend an unavailable branch must specify zero. Explicitly supplied invalid optional pump/fluid values no longer select defaults. Zero-capacity utilization is explicitly nullable. These are intentional boundary/serialization changes and are covered by the Phase 1 algorithm identity.
- PH0-003 (shared-network capacity), PH0-004 (equipment ownership), PH0-005 (terminal service assessment) and PH0-006 (automatic transfer policy) are not repaired here. Their design assumptions and deferred dispositions remain intact.

Verification entry points: `npx vitest run tests/phase1-numerical.test.ts` and `npx vitest run tests/twin-physics.test.ts tests/twin-network.test.ts tests/twin-integration.test.ts`. Full required gates, historical reproduction commands, raw outputs and measured environment belong to `ACCEPTANCE.md` and the Phase 1 requirement matrix.

## Integration and remaining numerical entry points

The shared `validateDesign`, `validateEvents` and `validateState` boundaries validate runtime values before engine work. Complete design identity is carried by standalone state, not just a caller-controlled revision label. Root asset/parent/domain/edge/port references must exist; disconnected or ambiguous valid paths retain the implemented unsupported outcome. Missing shore supply cannot masquerade as a live source. Candidate state is cloned, physically/range checked and checked against the complete serializable project envelope before publication. Hydraulic head/conservation/coupled-dispatch safeguards produce failure rather than a warning attached to success. Tests include a finite extreme loop that initializes with pumps disabled, then fails real bounded hydraulic work when a recorded pump command starts it; the previous valid state stays unchanged.

`routeLengthM` validates bounded three-coordinate SI input, preserves zero length and signed coordinates, and detects finite-coordinate subtraction/sum overflow. `loopGeometry` checks derived lengths. `buildDesign` retains the existing finite bounded configuration validator and deterministic formulas; runtime/imported graph data additionally passes the shared design validator. Geometry packing and graph inspection are diagnostics over that same validated representation, not new simulation models.

`billOfEquipment` validates configuration/graph and the nonnegative multiplier and checks every cost row, range and aggregate for overflow. Existing cost assumptions are unchanged. `sizingAssessment` validates its optional USD budget; its existing terminal-only assessment is unchanged. `marineScreen` keeps missing mass/unsupported geometry explicitly unassessed/null and checks successful scalar outputs. `summarize` validates state and aggregates before exposing current values; undefined PUE remains null. CSV/report entry points consume these same validated states and checked calculations. Existing provenance labels and default raw-data exclusions remain intact.

The preserved Legacy experience uses `src/domain/model.ts`: `simulate` calls `validateScenario`, which noncoercingly checks every bounded scalar before calculating. Its fixed positive flow denominator, bounded counts/powers/PUE and existing integer inventory rules keep all admitted arithmetic finite. It has no iterative solver or continuation state. Its existing negative temperature headroom and inadequate supply warnings remain valid outcomes; original tests and all three-browser Legacy cases are rerun unchanged. No Legacy equations, economic assumptions or design-peak/utilization relationship changed.

The numerical contract now also rejects sparse grid-allocation arrays, so omitted entries cannot become JSON null in a nominal successful result. Shared module/domain allocation ceilings bound that helper's loops. Generic project validation rejects array accessors/custom serialization, object accessors/nonenumerable/symbol properties and duplicate JSON keys before authoritative data can be transformed or dropped.
